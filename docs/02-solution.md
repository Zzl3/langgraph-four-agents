# 方案与设计取舍

## 执行循环

`src/engine.py` 使用 LangGraph `StateGraph` 编排 `decide → execute → decide` 循环。决策器每轮只选择一个动作；执行器调用对应本地工具，把参数和结果追加到 trace，再将完整观察交给下一轮。模型可通过 OpenAI 兼容 JSON 接口运行；默认离线策略是显式 mock。两种模式共用同一工具和结果校验路径。

典型时段冲突路径：

1. 读取素材并检查规则。
2. 查询要求时段，观察到 18:00 已占用、19:00 可用。
3. 下一动作提交 19:00 草稿，标记 `pending_confirmation`。
4. 最终校验从工具证据重建状态，明确 `published=false`。

若原要求时段可用，流程保存原时段并返回 `ready`；如果素材风险或读取失败，则阻断保存并返回未完成结果。保存时出现并发占位冲突会重新查询时段。

## 业务保护

- `read_material`、`check_rules`、`query_slots`、`save_draft` 是唯一排期工具。
- 保存工具核对素材审核、时段查询、用户原始要求、替代时段可用性及确认状态。
- 替代时段需符合精确的待确认状态和文案，任何路径均不允许发布。
- SQLite 事务内检查并写入；按原始请求计算幂等键。重复内容返回 duplicate，不同草稿冲突或时段竞争则拒绝。
- 最终结果只从执行轨迹重建；模型不能把失败结果改写成成功。
- `--max-calls` 为工具调用上限；触顶返回明确未完成状态和已完成轨迹。

## 取舍和限制

素材、规则和排期查询使用本地合成数据，方便复现和故障注入。SQLite 只协调同一个 runtime 文件，不与外部排期系统共享并发锁。审核依赖有限字段和禁词规则，不能替代人工合规审核。时间段查询结果可能在真实外部系统中发生变化。

LangGraph 负责状态图、条件路由与循环，不负责业务规则、模型质量或证据正确性。版本范围见 `requirements.txt`；当前实现使用 LangGraph 1.2.x 的 `StateGraph`、`START`/`END`、条件边和状态传递。
